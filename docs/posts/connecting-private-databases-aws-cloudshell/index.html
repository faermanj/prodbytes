Connecting to Private Databases with AWS CloudShell

2026-09-03

Previously on this series, we created a serverless PostgreSQL database on the isolated subnets of our three-AZ VPC, and left with a problem on purpose: private means private, so we can’t connect to it from the internet. Today let’s solve that and dive a little deeper into security along the way. Both stacks are created with CloudFormation, and the templates are available in the DSP repository, under samples/vpc-3az and samples/rds-pgsql-sls. The database stack’s outputs have everything we need: the cluster ARN, the host address, and even the CLI commands for the connection.

The password lives in Secrets Manager

The first step in those output commands is fetching the database password, and it comes from AWS Secrets Manager. That’s because the template asks RDS to manage the master password instead of setting one explicitly, with the ManageMasterUserPassword property on the cluster. RDS generates the password, stores it in Secrets Manager, and rotates it for me. On the cluster page in the console you can see “manage master user password” enabled, and on the Secrets Manager console the secret is right there; “retrieve secret value” shows the actual password.

Be mindful that Secrets Manager charges forty cents per secret per month in us-east-1 nowadays. There’s not much we can do about this one, since it’s generated by RDS, and for database credentials that need automatic rotation it’s a great fit. For other kinds of secrets we’ll look at Parameter Store in the future, which is more cost effective.

VPC endpoints

There’s a catch, though. The database is on isolated subnets, which have no internet access, and Secrets Manager is a service you normally reach over the internet. So how do we fetch the password from inside?

That’s where VPC endpoints come in. A VPC endpoint connects a specific AWS service to your VPC from the inside, so traffic to that service never has to leave for the internet. That’s good for security, of course, and also for cost, because you don’t pay for traffic going out and back in through internet gateways. It’s usually not a huge cost, but not wasting is better, even when it’s just a little.

A shell inside the VPC

To actually connect to the database and run queries, we need a compute resource inside the VPC. There are many ways to get one: an instance, a container, a function. One easy way is AWS CloudShell, a shell you use in the AWS console, just like the terminal on your computer, but running next to your resources. CloudShell supports VPC environments, which place the shell inside a VPC of your choice.

So I create an environment called dbshell, select the VPC we created, and the same isolated subnet the database is using. For the security group, the template already prepared what we need: it creates one security group for the service and one for the clients, and the database cluster authorizes connections coming from the client security group. So I pick the client security group for the CloudShell environment, and that’s what authorizes my connection. Security groups work like firewalls, and this service-and-clients pair is a pattern you’ll see a lot in enterprise setups: instead of authorizing addresses, you authorize whoever carries the client group.

Connecting, and the usual database work

Once the environment is up, it’s a regular shell, and the commands from the stack outputs work as-is. The first one fetches the secret with the CLI, stores it in the PGPASSWORD variable, and passes it to psql, connecting to the cluster address:

PGPASSWORD="$(aws secretsmanager get-secret-value 
  --secret-id <secret-arn> 
  --query SecretString --output text | jq -r .password)" 
psql -h <cluster-endpoint> -U postgres -d postgres

Copy, paste, and there it is, we’re connected to the database. From here the usual operations work as expected:

CREATE TABLE todo_item (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title text NOT NULL,
  done boolean NOT NULL DEFAULT false
);

INSERT INTO todo_item (title) VALUES ('Buy milk');

SELECT id, title, done FROM todo_item;

Create a table, insert the “buy milk” item, select it back, it’s there. I’ll leave the rest of the operations to you: this is the setup you’d use to debug your database, add data, and check what’s in and what’s not. When you’re done, drop the table, drop the database, or keep using it for your apps. And as always, don’t leave resources running that you don’t need anymore.

The point here is one way to connect to a private database, using CloudShell. We’re going to see others in future videos, so stay tuned. How does your team reach its private databases, bastion hosts, VPNs, something else? Let me know in the comments, and see you in the next one!
